# ADR 0009：M8／M9 的范围、时间轴与内容边界

日期：2026-10-26。状态：范围决策已采纳；M8 协议与覆盖层实现见 [ADR 0010](0010-m8-media-overlays-and-discovery.md)，M9 投屏／下载仍需专项 spike。详细工作包与验收见 [总开发计划第 11 节](../development-plan.md#11-m8m9详细开发计划)。

## 背景

v1.0.0 已通过托管 CI 并正式签名发布。既有路线图仍把 M8 写成 5–10 人日起的字幕／弹幕／发现增强，把 M9 写成直播、番剧、投屏、下载、多账号的集合；这不足以支撑实现排期，且版本编号仍停留在最初的 v0.1.0／v0.2.0 草案。

当前播放领域以 UGC 的 videoId／partId 建模，没有字幕／弹幕领域契约，也没有番剧与直播的能力区分。物理 TV、人工音画同步和真实账号写入仍未验收，M7 诊断中存在单点 avsync 异常。

## 决策

1. 保留 Flutter + Riverpod Notifier／AsyncNotifier + Freezed + MVVM／整洁架构，复用 Dio、Drift、media_kit 和唯一 PlaybackCoordinator。skill 中示例性的 ChangeNotifier 不替代本项目已确定的 Riverpod 方案。
2. M8 按“协议／时钟 spike→媒体时间轴→字幕→只读弹幕→UP／关注／搜索筛选→回归”推进。点赞／投币是独立、可延后的增量，不因规划授权执行真实写入。
3. 字幕／点播弹幕由原生媒体时钟及播放代次驱动；逐帧覆盖层与根页面状态分离。关闭、换内容、后台与退出取消工作并清空，不保持隐藏的高频动画。
4. 字幕首批只做已验证的 JSON 轨道，优先 Flutter 覆盖层。弹幕绘制优先评测现有 canvas 库；不先自写通用弹幕引擎，也不在 spike 前固定候选库为生产依赖。
5. M9 先引入类型化 PlaybackTarget、ResolvedPlayback、PlaybackCapabilities 和内容隔离的历史键，再分别完成 PGC 与直播。它们不复用 UGC ID、心跳协议或进度条假设。
6. 投屏按 TV 接收端单独评估，下载先做前台 UGC 与离线双轨播放，多账号最后做“多个保存、单一活动”。各自协议／设备条件不满足时可延期，不阻断已完成模块发布。
7. 后续版本从 v1.0.0 演进，M8 建议 v1.1.0，M9 的 PGC／直播建议独立版本；实际发布时才修改 pubspec 和标签。公共 Release 维持 ARM32／ARM64，x86_64 供 CI 模拟器。
8. 稳定性仍按用户确定的 15 分钟执行；物理设备、人工音画和真实账号操作分别验收，不以自动采样替代。已有 avsync 异常保留诊断，持续可复现漂移须先修复。

## 影响与待定项

- M8 全量估算修正为 18–27 人日，M9 核心 21–32 人日；缓冲、可选项和排期假设详见计划。
- M8 偏好缺字段兼容旧安装；无实际持久数据需求不升级 Drift。M9 类型化历史再做 v2→v3 及 v1→最新迁移，可选模块按需追加。
- 新 B 站契约当前只是固定上游线索，需要真实只读 spike；不直接移植 App gRPC 凭据或生成代码。新增协议与依赖来源／许可须记录。
- 投屏协议、下载后台组件、只读直播聊天室及精确弹幕库仍待验证。此项记录最初文档规划的边界；用户随后授权 M8 实施，具体结果与新增依赖由 ADR 0010 记录。
